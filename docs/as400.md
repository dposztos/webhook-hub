# Db2 for i (AS/400) from a script action

Script actions can query an IBM i over ODBC. This is the part of a Linux setup
people usually get stuck on, so here is the whole path, with the reasons.

## Why a separate image

IBM ships the i Access ODBC driver as a **glibc** binary, for **amd64, i386 and
ppc64el**. The default Webhook Hub image is Alpine (musl), so the driver cannot
run in it, and there is no arm64 build at all — an Apple-silicon or Ampere host
cannot run this driver natively.

`docker/prod/Dockerfile.db2` therefore builds the same application on Debian,
with:

- `python3` and `python3-pyodbc` from Debian,
- `unixodbc`,
- `ibm-iaccess` from IBM's public package server
  (`https://public.dhe.ibm.com/software/ibmi/products/odbc/debs`).

The build fails if the driver does not register itself, so a broken image is
never produced silently.

CI publishes it from the `script-actions` branch, tagged `db2` (plus a dated and
a commit tag), **never** `latest`:

```bash
docker pull ghcr.io/dposztos/webhook-hub:db2      # or dposztos/webhook-hub:db2
```

Building it yourself works the same way:

```bash
docker build -f docker/prod/Dockerfile.db2 -t webhook-hub:db2 .
```

Either way, name the image in `.env` and run the DB2 compose file:

```dotenv
APP_IMAGE=ghcr.io/dposztos/webhook-hub:db2
```

```bash
docker compose -f docker/prod/compose.db2.yml up -d
```

Check what landed in the image:

```console
$ docker compose exec app odbcinst -q -d
[IBM i Access ODBC Driver]
[IBM i Access ODBC Driver 64-bit]
```

## Credentials

They go on the container, never into a rule — that keeps the password out of the
database and out of the UI. In `.env`:

```dotenv
AS400_HOST=ibmi.example.local
AS400_USER=WEBHOOK
AS400_PASSWORD=…
AS400_LIBRARIES=MYLIB,OTHERLIB
AS400_NAMING=0
AS400_COMMIT=0
```

`scripts/as400.py` turns those into a connection:

```python
import as400

rows = as400.rows("SELECT ORDNO, CUSTNO FROM MYLIB.ORDERS WHERE ORDNO = ?", 42)
```

## Check the connection first

```console
$ docker compose exec app python3 /app/scripts/as400_check.py
{"ok": true, "server": "IBMI", "user": "WEBHOOK", "server_time": "2026-08-31 12:00:00"}
```

A failure prints the ODBC error instead, which is usually enough to tell what is
wrong:

| Message | What it means |
| --- | --- |
| `CWBCO1049 … not started, or blocked by a firewall` | The host servers are not running (`STRHOSTSVR *ALL` on the IBM i), or TCP 8471 is closed between the container and the system. |
| `CWBSY0002 … user ID or password` | Wrong credentials, or the profile is disabled (`*DISABLED`) after failed sign-on attempts. |
| `SQL0204 … not found` | Naming convention or library list: see below. |
| `SQL7008 … not valid for operation` | The table is not journalled and the connection is not in commit mode `*NONE`. |

## The four settings that cause most of the trouble

**Commit mode.** `AS400_COMMIT=0` (`CMT=0`, `*NONE`) is the default here on
purpose. Physical files that were never journalled — most of a classic RPG
application — cannot be read under any other isolation level, and the error
(`SQL7008`) does not mention commitment control at all.

**Naming convention.** `AS400_NAMING=0` is SQL naming: `MYLIB.ORDERS`, and the
library list is ignored. `AS400_NAMING=1` is system naming: `MYLIB/ORDERS`, and
unqualified names are resolved through the library list. Pick the one your SQL
is written for; mixing them produces `SQL0204` on tables that plainly exist.

**Library list.** `AS400_LIBRARIES=MYLIB,OTHERLIB` becomes `DBQ=MYLIB OTHERLIB`.
The first entry is the default schema for unqualified names.

**Character data.** The connection asks for CCSID 1208 (UTF-8) and pyodbc is set
to encode and decode UTF-8, so EBCDIC columns arrive as ordinary Python strings.
Columns tagged CCSID 65535 (binary — common on old files) are the exception:
they come back as bytes, and need `AS400_EXTRA=ALLOWUNSCHAR=1` or an explicit
`CAST(... AS VARCHAR(n) CCSID 37)` in the query.

## TLS

The Linux driver has no `SSL=1` keyword. IBM's own answer is stunnel: the
package ships a sample at `/opt/ibm/iaccess/doc/iaccess.stunnel.config`, which
maps a local port to the IBM i host servers over TLS, and the connection then
uses `localhost` as the system name. On a trusted internal network people
usually skip this; over anything else, do not.

## If ODBC is not an option

Db2 for i can also be reached over HTTP through XMLSERVICE (`itoolkit`), or with
JDBC via `jt400` from a JVM. Both avoid the native driver entirely, at the cost
of a slower path and, for XMLSERVICE, something extra to run on the IBM i.
